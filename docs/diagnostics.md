# 화면 및 리포트 오류 기록

2026-09-14 구현. 배포 후 수집을 시작한다. 과거 브라우저 오류를 소급 복원하지는 못한다.

## 운영자가 확인하는 방법

1. 서비스의 `/admin/diagnostics`를 연다.
2. `DIAGNOSTICS_ADMIN_KEY`를 입력한다. 별도 키가 없으면 기존 `COUPON_ADMIN_KEY`를 사용한다. 키는 브라우저 저장소에 저장하지 않는다.
3. 최신 50건을 조회하고 필요하면 이전 기록을 더 불러온다. 번호 검색은 **불러온 기록 안에서** 동작한다.
4. 고객이 전달한 오류 확인 번호로 찾는다. 화면 기록의 `requestId`와 서버 기록의 `id`가 같으면 같은 API 요청이다.
5. `stage`, `status`, `attempts`, `durationMs`로 실패 위치를 확인한다. 화면 오류는 `category`, `frames`, `release`, `screen`을 확인한다.

기본 화면은 오류만 표시한다. `성공 포함`으로 바꾸면 주요 API의 완료 기록도 확인할 수 있다. 조회 결과는 JSON 파일로 내려받을 수 있다.

## 수집 범위와 보관

- React ErrorBoundary, 처리되지 않은 JS 오류·Promise 오류, Vite 동적 모듈 로드 실패.
- 추가 질문, 유료 리포트 생성·복구, 결제 검증, 무료 결과 API의 상태와 처리 시간.
- 추가 질문 단계: 권한 확인 → 사용 여부 확인 → 질문 검증 → 원본 문맥 복구 → AI 생성 → 답변 형식 검증 → 답변 저장 → 사용 처리.
- 브라우저 최근 20건은 탭의 sessionStorage에 보관한다. 화면 오류 시 내려받기 버튼을 제공한다. 서버 전송 실패가 본 요청을 막지 않는다.
- 기존 `SAJU_KV`에 `diagnostic:v1:` 접두사로 14일 보관하며 Cloudflare 콘솔에도 구조화 기록을 남긴다. 새로운 DB 마이그레이션은 없다.
- 원문 오류 메시지, 질문·답변·사주·생년월일·이메일·리포트 접근 토큰·URL 쿼리는 신규 진단 로그에 넣지 않는다. 스택은 빌드된 `/assets/*.js:줄:열` 위치만 추출한다.
- 수집 엔드포인트는 동일 출처, JSON 형식, 최대 8KB, 허용 필드를 검사한다. 탭당 전송 20회, 서버 isolate별 IP당 분당 30회 제한을 둔다. 이는 전역 봇 차단을 보장하는 제한은 아니다.
- 개인정보를 넣을 수 있는 원문 메시지를 제외하므로, 일부 오류는 분류와 코드 위치만으로 조사해야 한다. 기존 다른 기능의 console 출력 전체를 정리한 변경은 아니다.

## 실패 복구 변경

- 추가 질문 실패 시 질문 입력을 지우지 않는다. 중복 클릭을 막고 대기 시간을 제한한다.
- 서버가 성공을 반환해도 답변이 비어 있거나 객체이면 화면 상태에 넣지 않는다.
- 답변 저장 후 질문권 사용을 기록한다. 저장 실패 전에 질문권을 소진하지 않는다.
- 응답이 유실되었거나 사용 기록 쓰기가 실패했더라도 같은 질문·같은 순번을 다시 보내면 저장된 답변을 돌려준다. 다른 질문으로 이미 쓴 순번을 재사용할 수는 없다.
- 네트워크 실패 시 '질문권은 사용되지 않았다'고 단정하지 않는다. 서버에서는 이미 완료됐을 수 있다.
- 이미 종료된 `gemini-2.0-flash` 대체 경로를 제거했다. 기본 재시도는 기존 `gemini-2.5-flash`를 한 번 더 사용한다. 프로젝트에서 검증된 대체 모델이 있으면 `GEMINI_FALLBACK_MODEL`로 지정한다.

## 2026-09-14 점검 결과

- 운영 `https://jobsaju.kr/` HTTP 200. 브라우저에서 가상 입력(1990-01-01, 시간 모름)으로 입력 → 소환 → 센척호랑이 무료 결과까지 정상 표시됨.
- 운영 `/api/diag`: HTTP 200, Vertex 전송 설정 및 KV 존재, 설정 모델 `gemini-2.5-flash`, `models_error: status 404`. 이는 모델 메타데이터 조회 결과이며 실제 생성 요청의 성공/실패를 뜻하지 않는다. 새 응답에는 `generation_checked: false`와 `diagnostic_probe: model_metadata`를 명시한다.
- 운영 구매 토큰을 사용한 실제 유료 추가 질문 생성은 미검증. 테스트용 구매 토큰과 배포 환경에서의 생성 확인이 필요하다.
- 기존 코드에 실패 후 입력 삭제, 답변보다 먼저 사용 처리, 종료된 대체 모델 사용이 확인되어 수정됨. 이것이 사용자가 겪은 모든 과거 장애의 원인이었다고 확정할 수는 없다.
- Google 공식 수명주기 문서상 `gemini-2.0-flash`는 2026-06-01 종료, 현재 주 모델 `gemini-2.5-flash`는 2026-10-20 종료 예정. 종료 전에 별도 품질 평가를 거쳐 모델을 교체해야 한다.

출처: https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/model-versions

## 검증과 남은 한계

- `npm.cmd run check`: 테스트, lint, TypeScript, 운영 빌드 확인. 기존 lint 경고는 남아 있다.
- 저장 실패 시 질문권 보존, 같은 질문 재전송 복구, 잘못된 AI 답변 거부, 타임아웃, 개인정보 제외, 관리자 인증, 저장소 실패 격리 테스트 포함.
- Cloudflare Pages 로컬 런타임에서 실제 KV 수집 및 인증 조회 확인.
- 별도 로컬 검증 번들에서 React 렌더 오류를 발생시켜 오류 번호 표시 → KV 저장 → 관리자 화면 조회를 확인했다. 화면과 서버의 번호가 일치했고, 빌드 파일·줄·열은 기록되며 오류 메시지의 테스트 이메일은 기록에서 제외됐다.
- 운영용 앱 번들에서 잘못된 테스트 토큰으로 복구 실패를 재현했다. 브라우저 `API_HTTP_ERROR`의 requestId와 서버 404 기록의 id가 일치했으며 테스트 토큰은 진단 로그에 포함되지 않았다.
- KV는 최종 일관성 저장소다. 서로 다른 지역에서 즉시 재시도하면 저장 반영 전일 수 있으며, 동시 요청을 전역에서 원자적으로 잠그는 변경은 아니다.
- 서버 실행 자체가 강제 종료되거나 최초 앱 JS가 아예 로드되지 않으면 완료 로그/브라우저 수집 코드가 실행되지 않을 수 있다. Cloudflare 런타임 로그도 함께 확인해야 한다.
- 기존 D1의 `generating` 상태가 종료 없이 남는 상황, 재시도 제한에 도달한 기존 리포트의 복구는 자동 수정하지 않았다. 서버 로그의 `generation_lock`, `generating`, `retry_limit`로 구분한다.
- 소스 구현과 로컬 검증은 운영 배포 완료를 의미하지 않는다. 프론트엔드와 Pages Functions를 함께 배포해야 고객 오류 수집이 활성화된다.
